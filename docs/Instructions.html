OnePortal Documentation

How This App Works

OnePortal is an internal employee management portal built with Laravel and Blade. It's a generic template — not wired to any one company — so a new organization can stand it up with configuration alone, no code changes.

Overview

The app is split into two fully independent experiences:

Employee Portal

A Blade-rendered site at the root domain: dashboard, leave requests, employee directory, workforce visibility, and profile management.

Control Panel

A separate Filament-powered admin app at /control-panel, covering users, departments, attendance, and leave approvals.

An admin account is redirected straight to the Control Panel and cannot fall back to the employee pages — the two are kept deliberately separate.

Roles & Access

Access is controlled by a simple two-role system stored on the User model.

User (Employee)

  • View dashboard
  • Submit leave requests
  • View own leave history
  • Browse employee directory
  • Check in / check out
  • Manage own profile

Admin

  • Manage users, roles, departments
  • Force a password change on next login
  • Approve / reject leave requests
  • Edit attendance records
  • View workforce dashboard widgets

Core Features

Employee Dashboard

Leave balance, days used, pending requests, department/employment info, and an interactive calendar for the current month — click a day to open a pre-filled leave request, or click a second day to request a range.

Leave Management

Employees submit leave requests (dates, department, reason) and track status: Pending → Approved/Rejected. An approved leave covering today blocks check-in/out and shows an "on approved leave" message instead.

Employee Directory & Workforce Visibility

Search and filter employees by department; see live status per employee — Remote, On Site, or On Leave.

Profile & Theme

Employees manage their own profile and avatar. A light/dark toggle in the sidebar is saved per-account (not just the browser), and every page shares the same set of CSS custom properties for consistent theming.

Authentication Flow

Sign-in is handled entirely through Microsoft Entra ID (Azure AD) OAuth 2.0 — there is no self-registration form.

Click "Sign in with Microsoft"
→
Redirect to Entra ID login
→
User authenticates
→
Callback with auth code
→
Exchange for token + profile
→
Find or create user
→
Logged in

On first login, if ENTRA_AUTO_PROVISION_USERS is enabled, a user record is created automatically from the Entra ID profile (name, email, object ID) with auth_provider = entra. On every subsequent login, the local profile is refreshed from the latest Entra ID data.

Setting Up For Any Company

Nothing in the codebase hardcodes a specific organization. To deploy a fresh instance for a different company:

  1. Register an application in that company's Azure AD tenant (see Entra ID Setup Guide below).
  2. Set APP_NAME and APP_URL in .env to the new company/domain.
  3. Set the four ENTRA_* environment variables to the values from that Azure app registration.
  4. Run php artisan migrate against a fresh database.
  5. Optionally seed departments/demo data, or just let employees sign in — accounts are auto-provisioned on first Entra ID login.
  6. Promote at least one user to admin (directly in the database, or via php artisan tinker) so someone can reach the Control Panel and manage the rest.
No source changes are required — branding, tenant, and user data are all environment/config or runtime (Control Panel) driven.

Entra ID Setup Guide

These are the steps to obtain the credentials the app needs (ENTRA_CLIENT_ID, ENTRA_CLIENT_SECRET, ENTRA_TENANT_ID, ENTRA_REDIRECT_URI).

1. Register an application

  1. Go to portal.azure.com.
  2. Navigate to Azure Active Directory → App registrations → New registration.
  3. Name it (e.g. "OnePortal") and choose Accounts in this organizational directory only.
  4. Click Register.

2. Copy the IDs

  1. Application (client) ID → ENTRA_CLIENT_ID
  2. Directory (tenant) ID → ENTRA_TENANT_ID

3. Create a client secret

  1. Go to Certificates & secrets → New client secret.
  2. Give it a description and an expiry.
  3. Copy the secret value immediately → ENTRA_CLIENT_SECRET (it won't be shown again).

4. Configure the redirect URI

  1. Go to Authentication → Add a platform → Web.
  2. Add the redirect URI(s), e.g.: 
    http://localhost:8000/auth/entra/callback
https://yourdomain.com/auth/entra/callback
  3. Enable Access tokens and ID tokens, then save.

5. Grant API permissions

  1. Go to API permissions → Add a permission → Microsoft Graph.
  2. Add: User.Read (delegated), User.ReadBasic.All (delegated), and Directory.Read.All (application, for the sync command).
  3. Click Grant admin consent for the organization.

6. Set the environment variables

ENTRA_CLIENT_ID=
ENTRA_CLIENT_SECRET=
ENTRA_TENANT_ID=
ENTRA_REDIRECT_URI=http://localhost:8000/auth/entra/callback

ENTRA_AUTO_PROVISION_USERS=true
ENTRA_SYNC_ENABLED=true
ENTRA_SYNC_BATCH_SIZE=100
ENTRA_SYNC_UPDATE_EXISTING=true

7. (Optional) Sync users from the directory

php artisan entra:sync-users
php artisan entra:sync-users --force
Troubleshooting: "Invalid state" errors usually mean stale cookies/session or a redirect URI mismatch. A login loop usually means the wrong ENTRA_TENANT_ID or an expired client secret. Permission errors mean admin consent hasn't been granted (or hasn't propagated yet — wait a few minutes).

Full reference: ENTRA_ID_SETUP.md in the repo root.
